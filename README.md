# Job Intake — личный поиск работы

Проект собирает вакансии, оценивает их по нескольким настраиваемым потокам поиска и
помогает выбирать варианты и вести отклики в локальной CRM. Поиск ориентирован на
широкий охват: удалённая работа с возможностью найма из Бразилии либо работа в São Paulo,
рабочий язык — английский. Неясные условия остаются доступны для ручной проверки.

Главная продуктовая цель — доходить до интервью с командой. Реализованы сбор,
отбор и CRM с историей этапов, контактами, реферальными маршрутами и следующими
действиями. История из `JobCRM.xlsx` импортируется без изменения исходной таблицы.
Генерация резюме и материалов для отклика относится к третьему этапу.

## Что уже работает

- Четыре независимых профиля: Product Management, Analytics Leadership, Business
  Analytics и Data Science Management. Одна вакансия получает отдельную оценку
  по каждому включённому профилю.
- DailyRemote, публичные API Greenhouse, Ashby и Lever, HTML-страницы компаний и
  смешанная watchlist. ATS передают полные описания; DailyRemote может догружать
  описание из страницы вакансии.
- Вакансии из выбранных писем Gmail через подключение в Codex и из локальных `.eml`:
  отдельные карточки, очищенные ссылки и оценка по всем включённым профилям.
- Явные ограничения, причины оценки, вопросы для проверки и категории A/B/C.
  Низкое соответствие сохраняет вакансию для просмотра.
- SQLite с историей событий и feedback, широкий CSV и локальный HTML-отчёт
  с фильтрами по профилю, результату, тексту и порядку сортировки.
- Переоценка сохранённых вакансий после изменения критериев без обращения
  к источникам, AI или Telegram.
- Разметка исходных текстов с точными цитатами и ссылками на фрагменты источника;
  опциональное извлечение и независимая проверка разными моделями.
- Независимое сохранение вакансий: сбой другой страницы, компании или источника
  не откатывает уже записанные результаты.
- Редактируемая CRM: отклик из сохранённой вакансии или вручную, профиль поиска,
  канал, этап с датой, контакты, реферальный статус, следующее действие и срок,
  заметки и метка версии резюме.
- Импорт JobCRM, экспорт истории CRM в CSV и воронка за выбранный период.
  Цель по умолчанию — четыре интервью с командой за месяц при ориентире десять
  часов поиска в неделю.

AI и Telegram выключены по умолчанию. Сбор запускается вручную командой `run`;
встроенного расписания нет. CRM запускается вручную на локальном адресе.

## Запуск из папки проекта

Нужен Python 3.11 или новее. Для нового окружения:

```bash
python3.11 -m venv .venv
.venv/bin/python -m pip install -e '.[dev]'
```

Следующие команды выполняются из корня репозитория. Относительный путь к SQLite
рассчитывается относительно текущей рабочей папки.

```bash
# Посмотреть активные профили и поисковые слова
.venv/bin/job-intake profiles --config config/settings.yaml

# Собрать вакансии из включённых публичных источников и сохранить оценки
.venv/bin/job-intake run --config config/settings.yaml

# Создать широкий список и HTML для ручного отбора
.venv/bin/job-intake export-csv --config config/settings.yaml --output data/local/jobs.csv
.venv/bin/job-intake render-html --config config/settings.yaml --output data/local/review.html --limit 500

# Открыть редактируемую CRM
.venv/bin/job-intake crm serve --config config/settings.yaml
```

`run` обращается к сайтам. При частичных ошибках он выводит причины и завершает CLI
с ненулевым кодом; успешные записи сохраняются. Откройте `data/local/review.html` в браузере:
это локальный отчёт, для его фильтров нужен JavaScript. Изменения в базе появятся
после следующего `render-html`.

CRM доступна на [http://127.0.0.1:8765](http://127.0.0.1:8765). Для её работы команда
`crm serve` должна оставаться запущенной; `Ctrl+C` останавливает сервер, сохраняя
данные в SQLite. Порт можно изменить через `--port`, базу — через `--database`.

## CRM откликов и рефералов

Во вкладке вакансий можно создать отклик и выбрать поток поиска. Исторический или
внешний отклик можно добавить вручную. Повторное добавление той же сохранённой
вакансии открывает существующий отклик.

В «Найденных вакансиях» доступны фильтры A/B/C, границы баллов (включительно)
и сортировка по категории или баллу в обе стороны. При выбранном профиле используется
его оценка; для всех профилей выбирается лучшая категория, затем решение по условиям,
балл и ID профиля. Оценка, используемая фильтрами, выделена в карточке. Внутри
категории вакансии идут по убыванию баллов; записи без актуальной оценки — в конце.
Фильтры оценки работают сразу и не изменяют воронку откликов.

Кнопка «В архив» скрывает найденную вакансию из активного списка. Фильтр «Архив
вакансий» переключает активные, архивные или все вакансии; в архиве доступна кнопка
«Восстановить». Архив сохраняется после повторного импорта и переоценки; исходный
текст, разметка, оценки, связанный отклик и его заметки сохраняются. Новые прогоны
`annotate`/`reevaluate`, HTML/CSV-выгрузки и уведомления пропускают архивные вакансии.
При архивации отменяются ожидающие уведомления; автоматическая очистка архива не
удаляет его записи. История архивации и восстановления хранится в событиях вакансии.
Архив вакансии и этап «Архив» у отклика задаются отдельно.

Для массовой архивации отметьте вакансии флажками или используйте «Выбрать все в
списке», затем нажмите «Архивировать выбранные». Выбор ограничен текущими результатами
поиска и фильтров; скрытые вакансии снимаются с выбора. В архиве так же можно массово
восстановить выбранные вакансии. Группа сохраняется одной транзакцией: если вакансия
удалена или её архив изменён в другом окне, вся операция отменяется и список нужно
обновить.

Баллы — сумма весов совпавших признаков, а не шкала 0–15; верхнего предела нет.
Текущие пороги в `config/search_profiles.yaml`: A — от 14 баллов при пройденных
обязательных условиях и признаках целевой роли; B — от 6, если условия A не выполнены;
C — ниже 6 или исключающее ограничение. При необходимости проверки условий оценка
снижается на 3 (до нуля); при исключающем ограничении — 0 и C. Пояснение в CRM
показывает пороги из настройки каждого профиля.

В карточке отклика доступны компания, должность, ссылка, профиль, канал
`unknown`/`cold`/`referral`/`recruiter`, этап, дата отклика, заметки и метка версии
резюме, например `Analytics-v2`. Смена этапа записывается в историю с указанной
датой. Метка CV помогает видеть, какое резюме использовалось; файлы резюме и их
генерация пока не добавлены.

Контакты можно создавать и редактировать, связывать с откликом как рекрутера,
реферера, hiring manager или иной контакт и удалять связь. Реферальный маршрут
имеет состояния: не задан, найти контакт, запрос отправлен, реферал получен.
Наличие рекрутера в карточке не меняет канал отклика автоматически. Сообщения
контактам и заявки через CRM не отправляются.

Следующее действие и срок задаются вручную. Список действий группирует просроченные,
сегодняшние, запланированные шаги и шаги без даты для активных откликов.
Автоматические напоминания не создаются.

## Импорт JobCRM и экспорт истории

Замените путь в примере на свой файл. Сначала можно проверить состав импорта:

```bash
.venv/bin/job-intake crm import-xlsx /path/to/JobCRM.xlsx --dry-run
.venv/bin/job-intake crm import-xlsx /path/to/JobCRM.xlsx --config config/settings.yaml
.venv/bin/job-intake crm export-csv --output data/local/crm.csv
```

`--dry-run` выводит состав импорта без персональных строк: количество записей,
распределение этапов, имя файла, его идентификатор и предупреждения;
база и её каталог не создаются. В интерфейсе также доступен выбор XLSX с проверкой
состава перед импортом. Источник читается без сохранения изменений в Excel.

Импортируются `Applications` с колонками `Position`, `Company`, `Link`, `Status`,
`Recruiter` и справочник `Companies`. Сохраняются ссылки ячеек, исходные значения,
статус, номер строки и идентификатор файла. Пустой статус становится `saved`,
`Application Sent` — `applied`, `HR Screening` — `hr_screen`, `Rejected` — `rejected`,
«Написал рекрутеру» — `contacted`. `Duplicate`, `Not Remote`, `Not relevant` и
`Too difficult` сохраняются как `archived` с исходной причиной; строки дубликатов
не объединяются автоматически.

Отсутствующие даты остаются неизвестными. Канал импортированного отклика —
`unknown`, в том числе при наличии рекрутера. Импорт не восстанавливает этапы,
которые не записаны в таблице. Контактные строки и ссылки сохраняются без
придуманных имён; несколько ссылок в одной ячейке остаются исходной записью.

Повторный импорт того же трекера сохраняет изменения, внесённые в CRM. Сортировка
и вставка строк Excel не создают старые отклики заново: идентичность зависит от
компании, должности, ссылки и номера повторяющейся вакансии, а не номера строки.
Новая вакансия импортируется отдельно. Изменения статуса и рекрутера уже
импортированного отклика в Excel не перезаписывают CRM. Весь импорт фиксируется
одной транзакцией.

## Воронка и цель поиска

По умолчанию выбран текущий календарный месяц в часовом поясе São Paulo.
Период, профиль и канал можно изменить. Воронка считает отклики, HR screening,
интервью с командой и офферы по датам событий. Для каждого этапа один отклик
учитывается один раз за период. Этапы без известной даты показываются отдельно
и не подставляются в текущий месяц по дате импорта.
Для даты отправки приоритет имеет поле карточки, затем самая ранняя известная
дата этапа `applied`. Исправление поля меняет показатели, сохраняя исходную историю.

Конверсия каналов использует отклики с известной датой подачи в выбранном
периоде. В числитель попадают интервью с командой для этих откликов с известной
датой не позже конца периода. Для неизвестного канала, отсутствующей когорты
или неполных дат процент не рассчитывается. Текущий этап отклика и история
достигнутых этапов показываются раздельно.

В `config/settings.yaml` можно изменить цель и недельный ориентир:

```yaml
crm:
  team_interview_goal: 4
  weekly_time_budget_hours: 10
```

Цель сравнивается с датированными интервью за выбранный период. Десять часов —
ориентир планирования; фактически потраченное время автоматически не измеряется.

## Настройка потоков

Профили находятся в `config/search_profiles.yaml`:

| ID | Направление | Начальные запросы |
| --- | --- | --- |
| `product-management` | Product Management | Product Manager, Product Lead, Head of Product, Product Owner |
| `analytics-leadership` | Analytics Leadership | Head of Analytics, Analytics Manager, Head of Data, Product Analytics Lead |
| `business-analytics` | Business Analytics | Business Analytics Manager, Business Analyst Manager, Head of Business Analytics |
| `data-science-management` | Data Science Management | Data Science Manager, Product Data Science Manager, Head of Data Science, Data Science Lead |

У каждого потока можно изменить:

- `enabled` — участвует ли он в поиске и текущем отчёте;
- `keywords` — запросы к DailyRemote; одинаковые запросы включённых потоков
  объединяются;
- `context` — описание искомой роли для дополнительной AI-оценки;
- `rules` — переопределения общих правил из `config/rules.yaml`;
- `scoring` — веса названий и содержания, приоритет компаний, сигналы и пороги
  A/B. Общие значения находятся в `defaults`.

Стабильный `id` связывает профиль с сохранённой историей. Изменение правил, весов,
названия или контекста создаёт новую версию критериев; сохранённые оценки становятся
устаревшими до следующей переоценки. Для пары вакансия–профиль хранится последняя
оценка, а не архив всех её версий. Изменение только `keywords` меняет
запросы для следующего сбора.

После изменения критериев:

```bash
.venv/bin/job-intake reevaluate --config config/settings.yaml
.venv/bin/job-intake export-csv --config config/settings.yaml --output data/local/jobs.csv
.venv/bin/job-intake render-html --config config/settings.yaml --output data/local/review.html --limit 500
```

`reevaluate` использует уже сохранённые данные и только детерминированные правила.
Он сохраняет даты публикации, первого обнаружения, последнего наблюдения и создания
записи; оценки и дата обновления меняются. Команда не догружает неполные описания.

## Отбор с приоритетом полноты

В `config/rules.yaml` включён `recall_first: true`. Разделяются решение и баллы:

| Решение | Что означает |
| --- | --- |
| `PASS` | Правила не нашли обязательных препятствий или вопросов, есть целевые сигналы |
| `REVIEW` | География найма, рабочий язык или другие условия требуют проверки; роль может быть смежной |
| `REJECT` | Найдено явное обязательное ограничение, несовместимое с настройками профиля, либо вакансия закрыта |

Например, «remote» без подтверждения найма из Бразилии остаётся `REVIEW`. Английский
текст объявления сам по себе не подтверждает английский рабочий язык. Несоответствие
семейству ролей в широком режиме становится риском для проверки. Обязательное
проживание в Германии не отменяется словами «contractor», «async» или «worldwide».

A/B/C выражают соответствие профилю. A требует `PASS`, целевого сигнала и достаточного
балла; `REVIEW` не превращается в A только из-за высокой оценки. C включает как
низкое соответствие, так и явные ограничения; эти случаи показываются отдельно.
Баллы складываются из весов совпавших признаков и поправок, а не нормализуются
к шкале 0–15: возможны дробные значения и оценки выше 15. В текущих профилях
порог A — 14, B — 6; высокая оценка сама по себе не подтверждает условия найма.

## Разметка текстов с опорой на источник

Разметка повторяет последовательность «источник → фрагменты → извлечение → проверка
→ подтверждённые сведения», применяемую в проекте Telegram knowledge base.
Исходные описания и метаданные сохраняются. Заголовок, локация, режим работы,
зарплата и явные поля рабочего языка или доступных стран становятся отдельными
фрагментами с идентификаторами и смещениями в оригинальном тексте. Описание
разделяется по предложениям и разделам; заголовки исходного HTML помогают восстановить
границы «о компании», обязанностей и требований даже после преобразования в одну строку.
Сведения о клиентах или офисах компании не подтверждают географию найма и не добавляют
сигналы соответствия роли. Отрицания и необязательные условия сохраняются в контексте.

По умолчанию включена локальная детерминированная разметка без вызовов моделей.
Она выделяет прямые поля источника и некоторые явно сформулированные условия.
Отсутствующие сведения остаются неизвестными: английский текст объявления не
подтверждает рабочий язык, а «remote» не подтверждает найм из любой страны.

Для переобработки уже сохранённых вакансий:

```bash
# Локальная разметка и переоценка; при необходимости ограничить число записей
.venv/bin/job-intake annotate --config config/settings.yaml --limit 100
```

Команда не обращается к сайтам или почте, не отправляет уведомления и не меняет
отклики, контакты и историю CRM. Даты публикации, первого обнаружения, последнего
наблюдения и создания вакансии сохраняются; разметка и оценки обновляются.
Неполное сохранённое описание остаётся неполным — команда не догружает его.

AI включается явно через `--ai`. Каждая стадия может использовать свой provider,
модель, имя переменной ключа, endpoint и reasoning. Поддерживаются Gemini, OpenAI
Responses, Anthropic Messages и совместимый Chat Completions (`mistral`, `deepseek`,
`qwen`, `zai`, `openrouter` либо `openai_compatible` с явным HTTPS URL).
Jev TypeSafe подключается только к проверке готовых утверждений.
Ключи задаются локально через переменные окружения; их значения не записываются
в `settings.yaml`. Без нужных ключей `--ai` сообщает о недостающей настройке.

```bash
# Бюджетный кандидат: GPT-6 Luna извлекает, Jev 1.13.0 проверяет
# Нужны OPENAI_API_KEY и TYPESAFE_API_KEY
.venv/bin/job-intake annotate --config config/settings.yaml --ai --preset budget-jev --limit 10

# Генеративная альтернатива: Gemini 3.5 Flash-Lite + Gemini 3.8 Flash
# Нужен GEMINI_API_KEY
.venv/bin/job-intake annotate --config config/settings.yaml --ai --preset balanced --limit 10
```

Пресеты не включают AI сами по себе и не меняют сохранённый YAML. Они предлагают
модели для сравнения; их фактическая точность на наших вакансиях пока не измерена.
Тарифы с первичными источниками, смешанная конфигурация и offline сравнение reviewers
описаны в [исследовании моделей](docs/model-research.md), проверенном 03.10.2026.
Старые поля `provider` и `api_key_env` продолжают работать. Stage overrides:
`extract_provider`/`review_provider`, `extract_api_key_env`/`review_api_key_env`,
`extract_base_url`/`review_base_url`, `extract_reasoning_effort`/`review_reasoning_effort`.

Первая модель создаёт черновые утверждения, вторая проверяет их по тому же источнику;
Jev выбирает статус каждого exact-ID утверждения и сохраняет probabilities/confidence.
Модели извлечения и проверки должны различаться. Каждое утверждение ссылается на
свой фрагмент и содержит точную непрерывную цитату. Проверка цитат допускает только
выравнивание пробелов и Unicode NFC; регистр, буквы и пунктуация сохраняются.
Цитата подтверждает происхождение текста, а смысл проверяется отдельно: выводы,
слабые доказательства, пропущенные условия и неподтверждённые ответы модели не
могут автоматически улучшить категорию вакансии. Уже найденные обязательные
ограничения сохраняют `REJECT`.

Полный текст передаётся в последовательных блоках с контекстом и идентификаторами
источника. Длинные фрагменты делятся без потери хвоста. Результаты этапов и расход
токенов сохраняются в локальном кеше `data/local/annotations`; повторный запуск
возобновляет обработку с незавершённого этапа. Кеш учитывает исходное содержание,
метаданные, конфигурацию, модели и промпты. Изменение источника требует новой проверки.
Смена reviewer использует сохранённое extraction; изменение источника, модели
извлечения или его промпта требует нового extraction. Provider, модель и endpoint
сохраняются по стадиям, отсутствующий usage помечается неизвестным.
Сбой части блоков, неполное описание или противоречивые условия оставляют вакансию
в `REVIEW`. Противоречия и непроверенные сведения сохраняются для ручного разбора.
В карточке вакансии CRM блок «Разметка и подтверждения» показывает цитаты, неизвестные
условия, противоречия и метод проверки. Разметка также хранится в SQLite отдельно
от исходных метаданных. Незавершённый AI review сохраняет статус `partial` даже
при локальной переоценке; непроверенное разрешение на работу или совместимость
часового пояса требуют ручной проверки. Двухэтапная модельная проверка выполняется только при
явно включённом AI и доступном ключе; локальная разметка не считается такой проверкой.
Разные aliases или gateways одной фактической модели не дают независимую проверку:
конфигурация различает настроенные identities, но не разрешает все vendor aliases.

Для сравнения reviewers на одинаковых вручную размеченных черновиках есть отдельная
команда без API и доступа к базе:

```bash
.venv/bin/python -m job_intake.annotation.benchmark \
  --gold data/local/benchmark/gold.jsonl \
  --predictions data/local/benchmark/reviewer.jsonl \
  --output data/local/benchmark/metrics.json
```

Формат JSONL и определения метрик приведены в [исследовании](docs/model-research.md).
Отчёт показывает точность подтверждений, цитаты, recall обязательных условий,
ошибочные подтверждения и полноту review. Он оценивает заданные drafts; полноту
извлечения и качество категорий A/B/C необходимо проверять отдельно. Live benchmark
без ключей не запускался.

## CSV и HTML

CSV по умолчанию включает A/B и низкие оценки C, исключая явные `REJECT`. По умолчанию
выгружается до 500 вакансий. В нём есть условия, описание, риски и оценки профилей.

```bash
# Ранжировать и отбирать по одному включённому профилю
.venv/bin/job-intake export-csv --profile analytics-leadership --output data/local/analytics.csv

# Только A/B
.venv/bin/job-intake export-csv --shortlist --output data/local/shortlist.csv

# Сохранить также явные ограничения для аудита правил
.venv/bin/job-intake export-csv --include-rejected --output data/local/all_jobs.csv

# Открыть HTML с выбранным начальным профилем
.venv/bin/job-intake render-html --profile product-management --output data/local/review.html --limit 500
```

HTML показывает все выгруженные записи: подходящие варианты, низкое соответствие,
явные ограничения и вакансии без актуальной оценки. Переключение профиля меняет
оценку и причины для той же вакансии. Доступны поиск по компании, роли и описанию,
фильтр результата, сортировка по баллам или дате первого обнаружения и ссылки
на источник и отклик.

Feedback сохраняется как заметка для последующей работы, без автоматического
обучения правил. Подставьте UID вакансии из CSV:

```bash
.venv/bin/job-intake feedback '<job_uid>' false_positive --note 'Проверить географию найма'
```

## Источники и полные описания

Источники включаются в `config/settings.yaml`, компании — в
`config/company_watchlist.yaml`. Текущая ATS-watchlist содержит Supabase и Wikimedia
Foundation. Старые HTML-конфигурации Stripe и Airbnb выключены до проверки селекторов.
Живая проверка 1 октября 2026 получила 48 вакансий Supabase и 11 Wikimedia с полными
описаниями, а также 12 карточек DailyRemote. На проверенных анонимных страницах DailyRemote
полное описание закрыто доступом; карточки сохраняются для ручной проверки.
Авторизованный сбор 2 октября 2026 по 15 запросам получил 437 уникальных вакансий
с полными описаниями. Для этого запуска лимиты были увеличены до двух страниц
на запрос и 1000 догрузок; прочитано 22 страницы выдачи. Пять запросов достигли
лимита страниц, поэтому это частичный охват каталога. Результаты и ручная подборка
сохранены локально в `data/local/`.

DailyRemote создаёт запросы `/remote-jobs?search=...` по `keywords` всех включённых потоков.
В текущих настройках
`max_pages: 1` ограничивает каждый запрос одной страницей, а `max_detail_fetches: 40`
задаёт общий лимит догрузок описания для этого источника за один запуск. Можно задать
`search_urls` вручную, выключив `use_profile_queries`. Пагинация следует `a[rel="next"]`
или текущей ссылке `a[aria-label="Go to next page"]`; можно задать свой `next_selector`.
Переходы ограничены исходным доменом страницы поиска. Пределы адаптера:
до 20 страниц на запрос и до 1000 догрузок.

Для чтения через вашу сессию DailyRemote задайте в локальном `.env`:

```dotenv
DAILYREMOTE_COOKIES_FILE=data/local/dailyremote.cookies.txt
```

Файл содержит одну строку — значение заголовка `Cookie` из запроса страницы
DailyRemote в Chrome DevTools: `name=value; other_name=value`. Префикс `Cookie:`
необязателен. Относительный путь считается от корня проекта. Cookies не выводятся
в логи и не сохраняются в базе; `.env` и `data/local/` исключены из Git. Храните
файл с правами `600` и обновляйте его при истечении сессии. В авторизованном режиме
сборщик делает только GET-запросы к `https://dailyremote.com/`, `/remote-jobs` и страницам
`/remote-job/<slug>`; каждый redirect проверяется до перехода. Другие домены,
HTTP, нестандартные порты и страницы управления аккаунтом не запрашиваются.
Отсутствующий или некорректный файл даёт ошибку источника, без анонимного fallback.
Если сессия больше не открывает полное описание, карточка сохраняется с
`detail_access: restricted` и `description_complete: false`.

Детали читаются из JSON-LD `JobPosting` или семантического селектора описания;
`detail_description_selector` позволяет указать свой CSS-селектор. Переходы и
перенаправления к деталям остаются на исходном HTTP(S)-origin. При ошибке, отсутствии
описания или исчерпании лимита сохраняется вся карточка с
`description_complete: false` и причиной в метаданных. Время сбора не подставляется
в дату публикации. В широком режиме явно неполное описание добавляет вопрос для
проверки и решение `REVIEW`.

Публичные ATS не требуют ключа для чтения этих endpoints:

| Тип | `params` | Данные |
| --- | --- | --- |
| `greenhouse` | `board_token`, `company` | `content=true`: полное описание, локация; дата редактирования отдельно от публикации |
| `ashby` | `board_name`, `company` | Полное описание, локации, `publishedAt`, опубликованная зарплата |
| `lever` | `site`, `company`; опционально `region: global` или `eu`, `page_size`, `max_pages` | Описание вместе со списками требований и заключением, локации, зарплата; ограниченная пагинация |

Для Lever по умолчанию запрашивается до 100 записей на странице и до 10 страниц.

Пример компании в watchlist:

```yaml
companies:
  - name: Supabase
    type: ashby
    enabled: true
    bucket: core
    params:
      board_name: supabase
      company: Supabase
```

Тот же `type` и `params` можно использовать как отдельный источник в `settings.yaml`.
Watchlist также поддерживает `type: html` и прежний формат с `careers_url` и селекторами.
Для HTML можно задать фиксированную `company`, `posted_at_selector` и
`detail_description_selector`; последний включает догрузку, если `fetch_details`
явно не выключен.

Описание API: [Greenhouse Job Board API](https://docs.greenhouse.io/job-board.html),
[Ashby Public Job Posting API](https://developers.ashbyhq.com/docs/public-job-posting-api),
[Lever Postings API](https://github.com/lever/postings-api/blob/master/README.md).

## Вакансии из Gmail

Поиск в подключённом Gmail выполняется через Codex. Настройки выборки сохранены
в `config/gmail_search.yaml`: письма за последние 30 дней, до 100 сообщений,
оповещения LinkedIn, DailyRemote и других указанных рассылок. Для обновления
попросите Codex собрать вакансии из Gmail с этим конфигом. Используются поиск
и чтение выбранных писем; отправка, изменение меток и статуса прочтения не нужны.
Пароли Gmail и OAuth-токены в проекте не хранятся.
Первый импорт 2 октября 2026 прочитал 8 оповещений LinkedIn и DailyRemote,
сохранил 29 карточек вакансий и 116 оценок по четырём профилям. Краткие карточки
остаются для проверки полного описания, рабочего языка и условий найма.

Результат чтения Gmail передаётся в локальный импорт:

```bash
.venv/bin/job-intake import-gmail /path/to/selected-messages.json --config config/settings.yaml
```

JSON имеет формат `{"messages": [...]}` с MIME-деревьями результата
`gmail_batch_read_email`. Поддерживаются декодированные `body.content` из
подключения Codex и `body.data` в base64url из Gmail API. Вакансии из одного письма
выделяются отдельно, а повторы определяются по ссылке вакансии. Ссылки LinkedIn
очищаются от персональных tracking-параметров. В базе остаются текст карточки
вакансии, ссылка и минимальные сведения об источнике; адреса отправителя/получателя,
полные заголовки и вложения не сохраняются. Дата письма не выдаётся за дату публикации.
Краткое описание из рассылки сохраняется как неполное, а статус вакансии — неизвестный.

`import-gmail` работает локально: он не получает новые письма самостоятельно и
отключает AI и уведомления для этого импорта. Обычный `run` также не обращается
к подключению Gmail в Codex. Обновление Gmail и импорт — два шага одного запроса
к Codex; повторное выполнение импорта не создаёт новую запись для той же ссылки.

Можно импортировать выбранные письма без подключения к аккаунту. В Gmail выберите
меню письма → «Скачать сообщение», положите `.eml` в одну папку и выполните:

```bash
.venv/bin/job-intake import-email data/local/job-emails --config config/settings.yaml
```

Для включения этой папки в обычный `run` измените `enabled` источника
`email-vacancies` в `config/settings.yaml`. Локальные письма и промежуточные снимки
следует хранить в `data/local/`, который исключён из Git.

Если вместо подключения Codex настраивается собственный OAuth-клиент,
Google предоставляет `gmail.readonly` для чтения всего подключённого ящика.
Поисковый запрос и label ограничивают выборку приложения, а не права токена;
доступ только к одной метке этим scope не ограничивается.
См. [официальные scopes Gmail](https://developers.google.com/workspace/gmail/api/auth/scopes).

## AI, уведомления и данные

`llm.enabled` и `telegram.enabled` в `config/settings.yaml` по умолчанию равны `false`.
Если включить их, ключи задаются через переменные окружения, перечисленные в
`.env.example`. AI может оценивать `PASS` и `REVIEW`, сохраняя явные отказы. Кеш
раздельный для профилей; он учитывает полное сохранённое содержание и метаданные,
версию критериев, модель, конфигурацию AI и фактический текст промпта. Размер текста,
передаваемого AI, отдельно ограничивает `max_description_chars`.

Для мгновенных Telegram-уведомлений вакансия, её оценки и запись outbox фиксируются
в SQLite до отправки. Неудачная доставка остаётся ожидающей и повторяется при
следующем `run`. Это доставка с возможным повтором: если процесс завершится после
успешной отправки, но до сохранения подтверждения, сообщение может прийти ещё раз.
`digest` формирует A/B-дайджест и при включённых настройках отправляет его; расписание
для запуска команды не настроено.

База по умолчанию — `data/local/job_intake.db`. Этот каталог, локальные экспорты
в нём, `.audit/` и `.env` исключены из Git. CRM и сбор вакансий используют одну
настроенную SQLite-базу. Переменная `JOB_INTAKE_DATABASE_URL` имеет приоритет:
если в `.env` старой установки осталось значение `sqlite:///data/job_intake.db`,
замените его на `sqlite:///data/local/job_intake.db`. Старый отслеживаемый файл
`data/job_intake.db` не содержит новой истории CRM.

При открытии старой SQLite-базы добавляются недостающие колонки и таблицы
оценок профилей, outbox и CRM; существующие вакансии и события сохраняются.
Дедупликация вакансий опирается прежде всего на ID источника, затем на URL или
fingerprint. Одна вакансия из разных источников пока может остаться несколькими
записями: объединение таких идентификаторов ещё неполное.

Команда `prune` удаляет подходящие под её условия записи найденных вакансий.
Связанный отклик CRM, его история, контакты и заметки сохраняются; очищается
только связь с удалённой вакансией.

## Проверка и следующие этапы

```bash
.venv/bin/pytest
```

Проверки используют локальные фикстуры и временные SQLite-базы: ограничения,
независимые оценки, полные описания, сбои источников, кеш, outbox, экспорт,
HTML-отчёт и повторяемая миграция, атомарный повторный XLSX-импорт, историю CRM,
конверсии по датам, сохранение CRM при очистке вакансий и локальный HTTP-интерфейс.
Отдельная живая проверка выполнена для Supabase,
Wikimedia и одного запроса DailyRemote; весь набор запросов и Lever пока проверены
локальными фикстурами. Результаты пробного сбора — в `.audit/phase1-preview/`.

Третий этап — подготовка и адаптация CV, материалов для отклика и интервью под
выбранную вакансию. Сейчас CRM хранит метку использованной версии резюме.
Подробности текущей реализации — в [архитектуре](docs/architecture.md).
