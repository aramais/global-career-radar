### Реализация и проверяемое поведение

- **R00:** `storage/snapshot.py` и `scripts/snapshot_audit_state.py` создают новую
  копию через SQLite backup API в `mode=ro`/`query_only`. Файлы gold, оплаченные кеши
  и discovery проверяются до/после копирования; конкурентная запись прерывает выпуск
  snapshot. Проверяется фактическое восстановление и SQL digest; секреты не копируются.
- **R01:** `storage/source_state.py` вызывается до classify/prefilter/annotate/score.
  Неполная карточка сохраняет полное описание и недостающие детали. Новое противоречащее
  утверждение/условие сохраняется вместе с прежним, получает `source_conflicts`,
  REVIEW либо доказанный REJECT и cap не выше B. Подстрока внутри отрицания не считается
  прежним утверждением. Явное закрытие применяется; карточка с default OPEN не открывает
  закрытую вакансию. Полная новая версия заменяет прежнюю без переноса конфликта.
- **Защита записи:** `jobs.source_revision` — аддитивная колонка с default 1.
  Pipeline фиксирует ожидаемую версию до оценки; repository проверяет её и атомарно
  захватывает обновление. Прямой импорт неполного источника, оценённого без согласования,
  отклоняется. Повторная batch-запись использует новую версию, `observed=False`
  сохраняет `last_seen_at`. Исходник и заменённый `two_pass` сохраняются в `job_events`
  (`source_superseded` / `annotation_superseded`), отдельно от активной annotation.
- **R02:** `annotation/input_contract.py` версионирует точные units/sections/offsets,
  source identity и полноту. Ключи учитывают модель, endpoint, prompt/schema, effort,
  generation и разбиение; timeout/retries/API env/collection timestamp не являются
  новым модельным входом. Публичный `source_hash` не изменён. Legacy rebind требует
  доказанного входа и настроек, повторной проверки drafts/reviews и сохраняет исходный
  файл/usage provenance. `VacancyAnnotator.inspect_cached_review(record)` проверяет
  восстановимость без API, ключа и записи. Недоказуемые случаи остаются stale.
- **R03/R07:** адаптеры сохраняют `li/p/br/h*` и Ashby newlines. DOM mapping также
  восстанавливает границы старого плоского clean-текста без переписывания его байтов.
  Слово requirements внутри обязанности не меняет раздел. Новый
  `SOURCE_UNITS_VERSION=source-units-v4` отделён от прежнего `TEXT_VERSION`;
  зависимые classifier/model/profile версии меняются, исторические gold hashes — нет.
  Модельная классификация также привязана к точному prompt/title/duties и source ID,
  поэтому изменение collection metadata не оплачивает её повторно; legacy без
  доказанного input hash остаётся на прежней строгой проверке полного источника.
- **R04:** coverage и состояния `unmeasured|partial|measured|not_applicable`
  считаются отдельно для decision, profession, eligibility, ranking и каждого тега.
  Human label readiness отделена от полноты baseline и blind predictions.
  Comparative gates без сравнимых запусков имеют `insufficient_evidence` и
  `passed=False`. `other` не требует релевантностного ранга. Gold CLI/UI/workbook и
  сравнение классификатора явно читают архив; operational default не меняется.

## 2. Инварианты реализации

1. Полный источник не заменяется карточкой; реальные изменения обязанностей, закрытия
   и условий найма не игнорируются под предлогом сохранения полноты.
2. Оплаченный review сохраняется в истории. Несовместимый review помечается stale
   и не участвует в текущем решении; локальная fallback-разметка его не уничтожает.
3. Исторические `source_hash`, snapshots и человеческие метки остаются проверяемыми.
   Хеши меняются через версионированный контракт, а не глобальное удаление полей.
4. Кеш переносится только после проверки точного входа, unit IDs, sections, claims
   и prompt/model-контракта. Равенства нормализованного текста недостаточно.
5. `job_uid`, profile ID, CRM-связи и источники человеческих решений сохраняются.
   Группировка дублей не переносит метки между региональными версиями.
6. Неизвестность не становится ни доказанным блокером, ни подтверждённым допуском.
   Отсутствие покрытия не становится нулём ошибок или пройденным quality gate.
7. Любая платная попытка резервируется до отправки; повторы видимы, лимит общий
   для Search и моделей. Непроверенная вакансия не принимается ради достижения N.

### R10. Контролируемое применение к рабочей базе — M

**Аудит:** устаревание оценок, X1/X5/CLS-09. **После:** R01–R04 и регрессий тех

перед следующим платным discovery-циклом, а не для локальной переоценки.

1. На восстановленной копии выполнить миграции, rebind dry-run и детерминированный
   пересчёт. Отчёт показывает source drift, сохранённые/восстановленные/stale review,
   role/tier/eligibility changes и причины.
2. Проверить выборку переходов REJECT↔REVIEW↔PASS и A/B/C, потерю связей и snapshots.
   Не пытаться получить обещанные аудитом количества переходов любой ценой.
3. Подготовить конкретный diff применения. Отдельным операционным шагом применить
   миграции и offline reevaluate к рабочей базе. Перед apply проверить drift,
   сделать свежий backup и открыть короткое окно блокировки writers.
4. Повторить saved-eval с честным покрытием и сравнить агрегаты с offline bundle.

Существующая команда `job-intake reevaluate --config …` **пишет в SQLite**, но работает
без fetch/AI/уведомлений. У неё сейчас нет флага dry-run: использовать отдельную
конфигурацию копии или сначала реализовать предлагаемый read-only replay/diff.
Не подставлять несуществующий флаг в инструкцию выполнения.

**Приёмка:** CRM/history/FK не потеряны; notifications/outbox не пополняются пересчётом;
все выбранные оценки текущей версии либо имеют явную причину ошибки/stale; повтор
не меняет наблюдение вакансии и не требует новой оплаты. Rollback восстанавливает
согласованную пару schema/data и соответствующие manifest/cache версии.
При изменении данных между dry-run и apply переснять diff. Rollback не восстанавливает
старую R00-копию поверх новых человеческих/CRM действий: нужен свежий согласованный
срез и, если запись уже возобновилась, сохранение/replay последующих событий либо
совместимое обратное изменение. Проверить сценарий drift и конфликт записи отдельно.

### R11. Реализовать назначения P1/P2 и перенос в CRM — M–L

**Аудит:** X2 / CLS-01 / ANN-03, ANN-07 / GLD-06 / DSC-10. **После:** R05/R07/R10;
активация назначения — после решений D1–D3 ниже.

- Добавить независимые human/predicted purpose, `practice_suitability` и версию
  рубрики. Неизвестное назначение — отдельное состояние, не `none`.
  Предпочтительны независимые пригодности P1/P2: подходящая P1 может быть полезна
  для практики. Если нужен один enum/очередь, приоритет и взаимное исключение
  определяются явно; миграция сама не выбирает назначение за человека.
- Сохранить оси profession, role fit, hiring eligibility, purpose. P1 не вычисляется
  просто как A/B, P2 — как C/other. Учитывать реальные причины cap и сырой score.
- Suppression означает отказ дорогого P1-review, а не доказательство непригодности
  для практики. До рубрики P2 такие вакансии доступны отдельной очередью для решения.
- В discovery явно задавать `objective=training|p1|p2`. В training сохранить нынешнее
  разделение role relevance/географии. Для P1 использовать исправленные обязательные
  ограничения до платного selector; unknown eligibility сохранять явно.
- `discovery promote`: dry-run и идемпотентный импорт подтверждённых кандидатов,
  snapshot, discovery UID→storage UID alias и ссылки на человеческую метку.
  Не переносить машинный `accept` как human relevance и не создавать внешний отклик.
- CRM показывает P1/P2 и отдельные gold/discovery наборы без потери истории.
  Удобство переключения наборов — UX-задача, а не смешивание самих labels.

**Приёмка:** один исходник может быть релевантным, но недоступным для P1; его
пригодность для P2 определяется отдельно. Повтор promote не создаёт дубль и не
меняет статус существующего отклика. Labels привязаны к тому же исходному snapshot.

### R12. Восстановить устойчивый сбор и жизненный цикл источников — M

**Аудит:** SRC-02–03, SRC-07, SRC-09–10, SRC-12. **После:** R01–R03/R10.

- `source_runs` с success/partial/auth/error, coverage, деталями лимитов и warnings.
  Pagination limit — не всегда ошибка; paywall/неожиданная пустота — не тихий успех.
- Явная политика auth DailyRemote вместо неоговорённого anonymous fallback.
  Штатные `sources check`, `refresh-details`, `recheck-urls` вместо monkeypatch-скриптов.
- Detail refresh для новых/просроченных/неполных записей, round-robin между запросами;
  не тратить всё на первый stream и не перезагружать неизменный полный текст без причины.
- Сохранить published label и оценку даты с точностью/provenance, улучшить разбор
  location/salary/apply URL. Не выдавать оценённую дату за точную публикацию.
- Закрывать по отсутствию только после полного успешного snapshot нужной доски.
  Auth failure, фильтр титулов, page limit или partial fetch не закрывают вакансии.
  Ввести `missing_since`, период ожидания/повторное полное наблюдение и reopen.
  Failed/partial runs не увеличивают доказанный период отсутствия вакансии.
- Общая URL identity и aliases для переименованных ATS/watchlist компаний;
  clustering вместо массовой смены `job_uid` и слияния региональных записей.
- Выборку 13.10 сначала сопоставить и показать import diff; наличие файлов не равно
  разрешению на массовый импорт в рабочую базу.

**Приёмка:** источник не выглядит успешным после потери авторизации; неполный сбор
не закрывает отсутствующие jobs. Переименование компании сохраняет CRM/gold связи.
Один ограниченный end-to-end сбор не понижает полноту и не инвалидирует AI из-за наблюдений.

### R13. Измеряемая экономия, затем расширение каналов — отдельные пакеты M

**Аудит:** ANN-03–12, CLS-02/11, DSC-03/06/11/12, SRC-05/06/11; часть GLD-12.
**После:** R04–R06/R09/R10 для измерений; новые каналы — после R12.

- Сначала завершить имеющуюся `next-5`; затем создать независимые audit-выборки.
  Фиксированный N=10 strong, 60–80 C или batch16 из аудита — ориентиры стоимости,
  а не доказанные статистические условия. Цели, допустимая регрессия и бюджет
  эксперимента задаются заранее; малые N отражаются интервалами и `insufficient_evidence`.
- На одном frozen bundle сравнивать thinking reviewer, compact payload и chunk size
  **по отдельности**. Сравнивать scope/ограничения/ложный отсев и стоимость успешного
  человечески подтверждённого результата, а не только согласие двух моделей.
- Проверить prefilter на позитивных и смежных/P2 случаях, reason-primed и независимый
  verify. Высокое согласие screen/verify само по себе не доказывает якорение.
- `skill` и локальные seeds выводить из платного review только после проверки всех
  downstream consumers. `display_only` не равно независимому `SUPPORTED`.
- Раздельно учитывать input/output/thinking/cached tokens, стоимость retries и
  актуальность price snapshot. Просроченный тариф не даёт достоверной оценки экономии.
- Параллельный review/selector вводить после надёжного ledger: расходы уже отправленных
  задач учитываются и после достижения N; лишние результаты сохраняются вне целевой очереди.
- Доменные ограничения, freshness=90 дней и Search fast — A/B за настройкой.
  Не включать ATS-only/90 дней без измерения потерянных позитивов и свежести.
- Для этих A/B заморозить объединённый frame baseline и варианта. Слепо проверять
  также результаты только baseline, исключённые доменом/возрастом, rejected,
  uncertain и необработанные из-за fetch/budget. Сохранять N и вероятности включения;
  отсутствие текста или бюджета — неизвестность, а не отрицательная метка.
- Watchlist, Himalayas, Workday и обогащение LinkedIn-писем — отдельные spikes:
  проверить актуальные официальные API/условия, реальные ограничения найма и маленькие
  fixtures. После этого — по одному источнику с лимитом и метриками выхода.
  Известный ATS route не разрешает обход авторизации защищённых сайтов.

**Приёмка:** нет доказанной регрессии по согласованным задачам при достаточном покрытии;
иначе вариант остаётся экспериментальным. Экономии разных вариантов не складываются
без общего измерения. Новые каналы оцениваются по человеческим P1/P2 результатам,
цене и времени, а не по числу скачанных карточек.

## 7. Общая проверка и окончание работ

Для каждого PR — регрессии по изменённому контракту, затем установленные в проекте
`pytest` и `ruff`; чистота diff и обратная совместимость manifest/schema. Платные
провайдеры в функциональных тестах заменяются детерминированными fixtures. Полный
набор не является доказательством relevance, поэтому отдельно нужен human eval.

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m ruff check .
git diff --check
```

**Технический выпуск готов**, когда источник/annotation не теряются, архив не ломает
eval, версии и покрытие честные, rollback проверен, повторный запуск не вызывает
необъяснимую оплату, а региональные копии сохраняют собственную eligibility.

**Продуктовая цель достигнута**, когда на нескольких сопоставимых периодах есть
подтверждённый поток P1 и полезный P2 с известными расходами и человеческим временем.
Критерии объёма/периода и допустимой ошибки задаются пользователем. Пять машинных
accept или отсутствие ошибок в тестах сами по себе эту цель не закрывают.
