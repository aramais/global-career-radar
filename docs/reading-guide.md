# Как читать и поддерживать документацию

[Документация](index.md) · [Карта проекта](project-map.md) · [Сущности](entities.md) ·
[Методы](methods.md) · [Сценарии](workflows.md)

Для HR Automation удобен маршрут **задача → общая схема → нужная сущность → метод →
проверка результата**. Сначала выбери вопрос, который хочешь решить. Справочники
методов и датированные аудиты открывай по необходимости. Ниже — предлагаемый
порядок для владельца проекта; время обозначает ориентир на проход, а не норматив.

## Быстро вернуться в контекст за 5 минут

1. Открой [карту проекта](project-map.md), прочитай начало и схему подсистем.
2. Выбери строку в таблице ответственности модулей.
3. Перейди в [рабочий сценарий](workflows.md) или конкретный [метод](methods.md).

Результат прохода: понятно, какой компонент отвечает за вопрос и где проверять
ответ. Например, «почему A не попала в уведомления» ведёт к отдельным условиям
найма и outbox, а «как добавить следующий шаг отклика» — к CRM.

## Понять устройство за 20 минут

| Ориентир | Что читать | На какой вопрос ответить |
| --- | --- | --- |
| 5 минут | [Карта](project-map.md) | Какие данные приходят извне, что делает код, что решает человек? |
| 7 минут | [Сущности](entities.md) | Чем исходный текст отличается от оценки и отклика? Где живёт каждое решение? |
| 5 минут | `run`, `_evaluate_record`, `upsert_evaluations` в [методах](methods.md) | Как одна вакансия проходит обработку и сохранение? |
| 3 минуты | Один [сценарий](workflows.md) | Что изменит команда и как увидеть результат? |

После чтения закрой документы и своими словами опиши одну вакансию: от сайта
до возможного отклика. Если звено не получается объяснить, вернись к этому
разделу. Это практический способ обнаружить пробелы именно в твоём понимании проекта.

## Разобрать конкретный механизм за час

Выбери один вопрос, например: «почему неполная карточка не должна затереть
полное описание?». Затем пройди один и тот же путь на трёх уровнях:

1. **Поведение.** Найди правило в [архитектуре](architecture.md) или профильном
   руководстве. Сформулируй ожидаемый результат и исключения.
2. **Данные и код.** Открой `JobRecord` и `source_metadata` в
   [сущностях](entities.md), затем `reconcile_source` в
   [source_state.py](../src/job_intake/storage/source_state.py) и место его вызова
   в [pipeline.py](../src/job_intake/pipeline.py).
3. **Пример проверки.** Прочитай
   [test_source_reconciliation.py](../tests/test_source_reconciliation.py).
   В тесте найди исходные данные, действие и ожидаемое состояние. При необходимости
   запусти выбранный тест на его изолированных данных:

```bash
.venv/bin/python -m pytest tests/test_source_reconciliation.py -q
```

Результат прохода — объяснение механизма на одном примере: какие поля пришли,
какой метод их обработал, что сохранилось и какая проверка это подтверждает.
Читать весь пакет `annotation` для такого вопроса не требуется.

## Как читать запись о методе

Сначала найди **вход** и **результат**. Затем проверь **эффекты**: сеть, платные
запросы, запись SQLite, создание файла или уведомление. После этого прочитай
условия ошибки и связанные проверки. Полное тело метода понадобится, когда
поведение в справочнике уже понятно и нужно разобраться в конкретной ветке.

Особенно внимательно смотри на создание объекта. `build_pipeline` создаёт
`JobIntakePipeline`, который вызывает `Database.create_schema`. Поэтому экспорт
CSV или HTML через pipeline может мигрировать SQLite ещё до чтения вакансий.
Создание `CRMService` тоже инициализирует схему. Для чистого чтения существуют
отдельные процедуры с SQLite `mode=ro`; их маршруты указаны в [сценариях](workflows.md).

Символ можно найти из корня проекта:

```bash
rg -n 'def reconcile_source|class JobRecord' src/job_intake
rg -n 'reconcile_source\(' src/job_intake tests
```

Первый поиск находит определение, второй — вызовы и примеры поведения.

## На чём основан такой порядок

[Diátaxis](https://diataxis.fr/start-here/) разделяет документацию по четырём
потребностям: обучение действием, выполнение задачи, техническая справка и
объяснение. Автор предлагает обращаться к деталям по мере работы. Для этого
проекта из этого следует выбор страницы по текущему вопросу: сценарий для команды,
справочник для поля или метода, архитектура для причин и ограничений.

[C4](https://c4model.com/introduction) описывает архитектуру на нескольких уровнях
приближения: окружение, приложения и хранилища, компоненты, код. Здесь этот принцип
применён в переходе от схемы подсистем к модулям, сущностям и методам. Схемы карты
показывают нужные проекту уровни и не претендуют на полный набор формальных C4 диаграмм.

[Google Technical Writing](https://developers.google.com/tech-writing/one/documents)
рекомендует определять аудиторию и цель текста, выносить ключевое в начало и
организовывать материал вокруг потребностей читателя. Поэтому начало каждой
страницы должно помогать решить, нужна ли она для текущего вопроса.

Это обоснование структуры и предложенного маршрута чтения. Конкретные интервалы
5/20/60 минут выбраны для удобства работы с этим репозиторием.

## Как писать следующие страницы

Одна страница должна отвечать на узнаваемый вопрос. Краткий результат и назначение
помещаются в начало; подробности — ближе к месту, где они понадобятся. Для инструкции
полезен порядок: исходные условия → команда → ожидаемый результат → проверка.
Для справочника: символ → вход → результат → эффекты → ограничения → ссылка на код.

| Изменение в проекте | Что обновить вместе с ним |
| --- | --- |
| Новый модуль или другая граница подсистем | [Карту проекта](project-map.md) |
| Новое поле, статус, таблица или связь | [Сущности](entities.md) и подробный контракт, если поведение изменилось |
| Новый публичный метод, команда или маршрут | [Методы](methods.md), соответствующий [сценарий](workflows.md) |
| Изменение эффекта команды | Сценарий рядом с командой, примеры в README |
| Новая проверка или замер | Датированный отчёт с версией, данными, условиями и ограничениями |
| Новое объяснение или руководство | Ссылку в [указателе](index.md), чтобы страницу можно было найти |

Ссылки на код позволяют проверять детали; небольшие таблицы фиксируют основные
контракты. Полную копию исходников и перечень каждого внутреннего helper
поддерживать вручную нецелесообразно. При переименовании проверь ссылки и символы
через `rg`, а примеры команд сверяй с `--help` без запуска рабочей операции.

Подход [Docs as Code](https://www.writethedocs.org/guide/docs-as-code/) предлагает
вести документацию в обычном текстовом формате под контролем версий и проверять
изменения вместе с кодом. Здесь для этого достаточно Markdown в `docs/`, понятных
ссылок и проверки затронутых примеров; отдельный движок сайта пока не нужен.

У [Diátaxis](https://diataxis.fr/how-to-use-diataxis/) есть полезное правило
поддержки: улучшать конкретное место небольшими шагами. Новое руководство стоит
добавлять, когда возник отдельный повторяющийся вопрос, а существующее исправлять
вместе с изменившимся поведением.
