# Одна метка роли и одна оценка вакансии

Дата изменения контракта: 17.10.2026. Запрос: сначала определить основную профессию
вакансии, затем оценивать её релевантность по выбранной роли. Data Science Manager
не получает отдельные нулевые оценки соответствия Product Management и другим ролям.

## Карта зависимостей, собранная до изменения

| Участок | Прежняя зависимость | Новый контракт |
| --- | --- | --- |
| `models/job.py`, `profiles.py` | Результат на каждую пару вакансия–профиль; четыре активных потока | Стабильные ID сохранены; одна классификация выбирает критерии |
| `pipeline.py` | Цикл правил, скоринга и семантического rerank по всем профилям | Классификация перед выбранным скорингом; один результат |
| `annotation/ai.py`, `schema.py`, `service.py` | Факты и общие ограничения применялись к каждому результату | Факты сохранены; классификация имеет отдельный промпт и результат |
| `storage/models.py`, `database.py`, `repository.py` | Матрица `job_profile_evaluations`, вычисляемый лучший профиль | `jobs.role_label`, `role_classification`; `job_relevance_evaluations` с `UNIQUE(job_uid)` |
| `storage/queries.py`, `crm/jobs.py`, `crm/server.py` | Выбор лучшей категории, решения и score | Только текущая оценка выбранной метки; фильтр профиля отбирает вакансии |
| `crm/index.html`, `review/report.py` | Несколько оценок одной вакансии | Одна роль и её score; устаревание видно отдельно |
| Экспорт, digest, outbox | Источник решения — лучший профиль | Источник — единственная текущая оценка; существующие CRM-связи сохранены |
| `annotation/gold.py`, JSON Schema, CLI | Четыре ручные оценки relevance | v2: один `role_label` и одно число `relevance` |
| `annotation/accuracy.py` | Максимум relevance и лучший сохранённый score | Отдельная точность метки и качество одной оценки |
| `annotation/rules_diff.py` | Самостоятельный цикл по всем профилям вне pipeline | Одна роль в новом коде; исторический контракт явно обозначается |
| Тесты и документация | Количество результатов и запросов равно количеству профилей | Один результат, свежесть классификации, смена роли, миграция |

Отдельного поля `interest` в исполняемой модели не было: ручная интересность выражалась
через `relevance` 0–3, машинная — через `fit_score` и A/B/C. Все 19 фактических тегов,
включая широкий `role_family`, сохраняются. `role_label` отвечает за единственный
выбор критериев, а не заменяет доказательные характеристики вакансии.

## Проверенный план реализации

План проверен отдельным агентом до реализации. Обязательные условия проверки:

1. Выбирать профессию без личных предпочтений, весов fit score и оценки готовности
   кандидата; одинаковые слова разных ролей не разрешать максимумом релевантности.
2. Сохранять одну метку из включённых стабильных ID. `other` обозначает профессию
   вне таксономии либо неразрешённую неоднозначность; чужой профиль не оценивается.
3. Хранить роль и единственную текущую оценку атомарно. Смена метки заменяет текущую
   оценку; история CRM и исходные вакансии не удаляются.
4. Версионировать всю таксономию и политику классификации. Изменение соседней роли,
   исходника или критериев не должно оставлять действующим старый score или AI-кеш.
5. Сохранить офлайн-переоценку без запросов к источникам, моделям и Telegram.
6. Не переносить исторический argmax в метку. Старые результаты требуют переоценки;
   человеческие gold v1 требуют ручной миграции в отдельный файл v2.
7. Проверять классификацию и релевантность отдельно, включая неизвестные роли,
   ошибки модели, пропуски предсказаний, переключение фильтров и исторический diff.

Порядок изменений: контракт классификатора и версий → pipeline → таблица и
репозиторий → CRM/экспорт/outbox → gold/accuracy/rules-diff → проверки и документация.
Критерии личного поиска, численные веса, пороги и стабильные ID профилей не менялись.

## Миграция и эксплуатация

Создание схемы добавляет новую таблицу и поля, сохраняя историческую таблицу
`job_profile_evaluations`. Существующая матрица не определяет текущую профессию.
До переоценки такие записи показываются без актуальной оценки. После обновления
кода пользователь может запустить обычный офлайн `job-intake reevaluate`.
Это запись в рабочую SQLite, а не чтение. Изменение кода само по себе не запускает
эту команду и не переписывает приватные данные.

Классификация сохраняет метку, метод, объяснение, версию таксономии, source hash
и content hash. Явный титул разрешается локально. В разрешённом AI-режиме модель
может уточнить неопределённую роль по обязанностям и цитате. Сбой или неоднозначность
сохраняют `other` и необходимость ручной проверки. Релевантность `other` не оценивается
по чужому профилю; технический нулевой score не является оценкой личного интереса.
В CRM, HTML и CSV такая роль показывается как неоценённая, без численного балла;
обязательные ограничения и объяснение классификации остаются доступны.

`gold sample` создаёт `vacancy-tags-v2.jsonl` с `role_label: null`, `relevance: null`.
`gold validate` отклоняет v1 и не изменяет его. `eval accuracy` читает SQLite через
`mode=ro`, не мигрирует базу и не выбирает лучший старый результат. Точность метки,
покрытие и матрица ошибок отделены от precision/recall/NDCG релевантности.

`rules-diff` запускает каждую Git-версию в отдельном офлайн-процессе. Новая версия
возвращает ровно один результат на вакансию (`single-role-v1`). Версия без
классификатора сохраняет старую матрицу (`multi-profile-legacy`); смена контракта
отмечается явно. Snapshot проверяется согласно своему контракту.

## Проверки

Регрессии охватывают Data Science Manager против Product Manager, неоднозначную
таксономию, `other`, смену роли, замену текущей оценки, сохранность CRM, версии
таксономии/исходника, отсутствие legacy fallback, ручной перенос gold v1, независимую
матрицу ошибок меток и совместимость исторического `rules-diff`.

Основные команды проверки:

```sh
.venv/bin/python -m pytest -q
.venv/bin/ruff check src tests
```

Проверки используют временные SQLite и подставные ответы моделей. Дополнительно
на отдельной копии рабочей базы офлайн переоценены 100 вакансий: сохранены все
525 вакансий, 2100 исторических оценок и CRM; для переоценённых записей создано
ровно по одной текущей оценке. Рабочая база осталась неизменной, внешние модели
для этой проверки не вызывались.
