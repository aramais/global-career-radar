# P1: применение, назначения и источники

Дата выпуска: 2026-10-19. Инженерный P1 из плана аудита отличается от карьерных
назначений P1 («следующая работа») и P2 («практика интервью»).

## Два назначения в CRM

`job_purpose_assessments` хранит независимые человеческие и машинные решения
`suitable | unsuitable | unknown` для каждого назначения. Низкий score, C,
`other` и suppression сами по себе не назначают практику интервью.

Изменение критерия: `config/purpose_rubric.yaml`, поле `p2`: отсутствовавшая
согласованная рубрика → «аналитика/data с похожими задачами, даже если уровень
или найм не подходят для следующей работы». Основание — ответ пользователя
в чате проекта 19.10.2026. Версия `data-interview-practice-2026-10-19-v1`
закреплена в `purpose.py`; YAML сохраняет декларацию и происхождение решения.
Пороги 19/6, стабильные profile ID и личный юридический статус не менялись.

Машинная пригодность для практики требует доказательств аналитических задач
и сходства обязанностей. Неизвестность сохраняется явно. Для следующей работы
дополнительно требуется подтверждённая доступность найма. Это рекомендация,
человеческий ответ остаётся отдельным полем.
Подтверждённо закрытая вакансия не рекомендуется для реальных интервью; её снимок
может использоваться как учебный пример. Человеческие ответы при этом не заменяются.

CRM содержит очереди по назначениям и на проверку; ручное сохранение использует
версию и хеш исходника. Метки P1/P2 имеют отдельные source/rubric pins.
Подтверждение одной оси или правка заметки не актуализируют другую устаревшую метку.
Пересчёт не заменяет человеческие ответы; изменения журналируются.

## Контролируемое восстановление R10

Из корня проекта:

```bash
PYTHONPATH=src .venv/bin/job-intake repair prepare \
  --config config/settings.yaml \
  --output data/local/repairs/next-release
```

`prepare` создаёт новую проверенную резервную копию, мигрирует отдельную SQLite
и пересчитывает все записи, включая архив. Использует только доказанно совместимые
сохранённые разметки, без fetch, AI и уведомлений. Формирует `report.json`,
`report.md`, SHA и `candidate.db`; рабочая база на этом этапе не меняется.
Отчёт показывает восстановление кешей и переходы role/tier/eligibility с причинами.
Недоказуемый старый кеш остаётся stale и не переоплачивается автоматически.

После проверки конкретного diff:

```bash
PYTHONPATH=src .venv/bin/job-intake repair apply \
  --prepared data/local/repairs/next-release
```

`apply` проверяет хеши кода, конфигурации, файлов и логическое состояние базы,
делает свежую копию и захватывает SQLite writer lock. Переносит подготовленные
оценки транзакционно; исходные факты, даты наблюдения, CRM, человеческие метки,
feedback и outbox защищены сравнением. Сбой после commit определяется по ledger;
повторное применение идемпотентно. Drift требует нового `prepare`.

```bash
PYTHONPATH=src .venv/bin/job-intake repair rollback \
  --prepared data/local/repairs/next-release
```

Rollback восстанавливает прежние оценки из свежей копии перед apply. Совместимые
аддитивные колонки остаются, отсутствовавшие ранее значения становятся unknown.
Исходные JSONL и кеши не переписываются. Если после apply появились новые записи
CRM или человеческие действия, rollback отказывается их затирать: нужна новая
проверка и перенос последующих событий. Этот сценарий проверен регрессиями.

## Источники и перенос discovery

Фактический выпуск применён 19.10.2026 в
`data/local/repairs/p1-2026-10-19-final/`: 525 вакансий, CRM/human/outbox сохранены,
1361 исходный файл проверен, API calls=0. Результаты —
[verification](../data/local/repairs/p1-2026-10-19-final/verification.md).
Первый candidate `p1-2026-10-19` помечен INCOMPLETE и не применялся.
Для новых выпусков нужен новый каталог `prepare`; пример `next-release` выше
не переиспользует уже применённый diff.

```bash
PYTHONPATH=src .venv/bin/job-intake sources check
PYTHONPATH=src .venv/bin/job-intake sources refresh-details --dry-run --limit 20
PYTHONPATH=src .venv/bin/job-intake discovery promote --run RUN_DIR --objective p2
```

Эти формы команд читают сохранённое состояние. `sources check --live`,
`sources refresh-details --no-dry-run` и `sources recheck-urls` обращаются
к источникам; refresh сохраняет удачные обновления. `discovery promote --apply`
записывает подтверждённые кандидаты в HR без внешнего отклика и уведомлений.
Повторный promote не создаёт дубль. Если вакансия уже есть, сохраняется ссылка
на неизменяемый discovery snapshot; более свежий исходник HR не перезаписывается.
Человеческие ответы с другого снимка не объявляются текущими.

`source_runs` хранит полный/частичный результат, auth/error, coverage и лимиты.
Отсутствие вакансии закрывает её только после повторных полных успешных снимков
той же ATS-доски и семидневного подтверждённого периода отсутствия. Ошибки,
фильтры и лимиты не увеличивают этот период. Повторное появление в полной доске
открывает только вакансию, закрытую этим механизмом. ATS aliases сохраняют UID
и CRM-связи при переименовании watchlist; региональные варианты остаются разными.

Frozen evaluation, когорты и эксперименты описаны в [p1-evaluation](p1-evaluation.md),
изменения классификации — в [p1-role-policy](p1-role-policy.md), discovery —
в [p1-discovery](p1-discovery.md) и
